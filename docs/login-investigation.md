# 扫码登录阻塞：错误码 7

## 结论与边界

- **当前登录不可用。** 不应继续宣传「扫码即可登录」。
- 用户在 0.1.2 中的真实诊断是 `stage=failed, status=scanned, errorCode=7, serverReason=unknown`。
- 这证明扫码状态已被服务端观察到，但插件尚未取得登录会话；不是只差一个成功提示或窗口跳转。
- 错误码 7 的具体校验含义未确定。不能据此断言是 CSRF、签名、设备信息、风控或账号问题。
- 不打印/提交登录凭据、二维码 token、完整响应或真实账号存储。

## 已验证的修复与未解决部分

| 事项 | 验证 | 能否证明真实登录成功 |
| --- | --- | --- |
| Map 序列化、Cookie 域/路径/过期处理 | 完整模块模拟测试、MyGo 0.1.7 运行时测试 | 否 |
| API 错误不再被吞掉 | 模拟测试、用户已看到错误码 | 否 |
| 有会话后立即返回账号，不等待 `/me` | 完整模块与 MyGo 运行时模拟测试 | 否 |
| `x-tt-passport-csrf-token` 与当前 Cookie 一致 | 本地官方 SDK 源码、实际未扫码请求、模拟测试 | 否；0.1.2 真实确认仍失败 |
| 获得真实会话并进入个人曲库 | 尚未成功 | 否 |

一次受控的未扫码请求对比中，不带 CSRF 头、带匹配头、带不匹配头都返回 `status=new, error_code=0`。因此不能用未扫码响应来证明最终认证所需的校验已经满足，也不能用该对比判定 CSRF 无关紧要。

## 官方实现对照

只读检查了本机官方汽水音乐 3.5.1 的安装资源（不是用户账号数据）：

- `main.asar/assets/renderer-CGo_3avn.js` 中，Passport 请求拦截器从 `passport_csrf_token` 或 `passport_csrf_token_default` 取值，设置 `x-tt-passport-csrf-token`。
- 同一 SDK 还有浏览器信息处理和 `account_sdk_source_info` 请求参数。

先前取得的 [folia-qishui](https://github.com/2706521883-lgtm/folia-qishui) 参考实现中：

- `electron/qishui/qishui-auth-v6.js` 使用 Electron 隔离会话和浏览器窗口初始化官方安全 SDK。
- Passport 通用参数包括浏览器信息、`msToken`、设备/安装标识等；请求通过浏览器安全组件发出。
- 该参考实现会检查 `a_bogus` 和 `msToken` 是否注入；POST 请求还处理请求体摘要及请求头。
- 二次验证 2046 由独立官方验证窗口处理。
- 其原生 `/luna` 签名实现还存在 Windows x64 平台限制，不能直接当作 macOS 可用方案。

这些是与当前手写 `fetch` 请求的具体差异，**不是错误码 7 的已证实原因**。复制几个固定参数、生成随机“签名”或仅改成功状态都不能替代实际 SDK 认证。

## 后续工作应如何验证

1. 先确定 macOS 可用、允许使用的官方认证入口/SDK 运行方案，评估 MyGo 的 `host.webSignIn` 是否足够；不够再设计有最小权限的 helper。
2. 不自动读取/导出用户官方客户端的会话，不关闭安全验证，不引入来历不明的二进制。
3. 对照正式 SDK 的初始化、设备标识、Cookie、动态安全参数、请求签名和二次验证流程，而非继续只测 `status=new`。
4. 若需要新的用户协作采集，应先说明范围，限于一次受控尝试与脱敏结果；不要再次要求无目的地反复扫码。
5. 真正验收必须包括：手机确认 → 桌面取得非空有效会话 → `signIn()` 返回 → MyGo 关闭弹窗 → 成功读取用户信息或个人曲库。
6. 搜索/播放的签名、音频解析与转码另外验收，不能从登录成功推断它们可用。

当前自动化测试只能证明插件对预设响应的处理和运行时兼容性，不能证明服务端会接受这些认证请求。SDK、原生库等第三方资源的许可和分发条件也需在发布前单独确认；本仓库没有加入从官方安装包提取的资源。
